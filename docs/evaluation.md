# 推荐与评测设计

## 1. 为什么先用规则推荐

当前阶段的目标是验证用户是否需要“历史偏好 + 当日状态 + 推荐解释”的产品流程，而不是验证某个大模型。规则方案成本低、结果可复现、方便定位失败原因，也能建立后续比较 LLM 版本所需的基线。

## 2. 用户画像

系统从出游记录的地点、活动、餐饮和备注中识别偏好标签。评分达到 4 分以上会增加正向权重，选择“愿意再次体验”会继续加权。备注中的拥挤、距离、体力、噪音和性价比关键词会形成避雷标签。

## 3. 排序逻辑

每个候选方案由偏好匹配、每日状态匹配、新鲜度和近期重复惩罚共同评分。每日状态只在当天生效；最近两次记录中的标签会产生重复惩罚；历史中从未出现的标签提供少量新鲜度奖励。

这一设计不是为了寻找唯一最优解，而是用于生成三类方向：稳妥推荐强调高权重偏好，相似探索保留一个熟悉标签并更换场景，惊喜选项控制历史标签占比以增加探索性。

## 4. 人工评测维度

相关性用于判断结果是否匹配历史偏好和每日状态；约束满足用于判断是否避开明确的负向条件；解释一致性用于判断推荐理由是否和实际计分因素相符；多样性用于判断三个方案是否提供了真正不同的选择。

每个维度建议采用 1 到 5 分。若硬约束未满足，即使其他维度较好，也应将该用例判定为失败并记录原因。

## 5. 评测流程

固定使用 `test-data/evaluation-cases.csv` 中的场景。每次调整标签、权重或候选池后，重新运行相关案例并记录人工评分。除平均分外，还要保留失败案例、错误类型和修复动作，避免只展示正向结果。

## 6. 后续实验

规则版稳定后，可以增加 LLM 版本作为实验组。对比内容包括相关性、解释一致性、输出稳定性、响应时间和单次成本。LLM 不直接替换硬约束层，而是优先用于理解复杂备注、扩展候选方案和生成自然语言解释。
